\section{Contextualização}

O controle de entrada e saída de funcionários é uma atividade essencial para organizações que operam com turnos fixos ou escalas de trabalho. Métodos tradicionais, como cartões magnéticos, senhas ou registros manuais, apresentam limitações relacionadas à segurança, possibilidade de fraudes e baixa integração com sistemas analíticos.

Com o avanço das técnicas de Visão Computacional e Aprendizado de Máquina, especialmente no campo do reconhecimento facial, tornou-se viável implementar soluções biométricas com processamento local e custo relativamente reduzido. Dispositivos embarcados de baixo consumo energético, como o Raspberry Pi 4, permitem a execução de modelos de aprendizado de máquina diretamente no ponto de captura, reduzindo latência e dependência de infraestrutura centralizada.

Além do controle de acesso, a coleta estruturada desses dados possibilita análises logísticas relevantes, como cálculo de tempo médio de permanência, identificação de padrões de atraso e avaliação de horários de entrada e saída. Essas informações podem apoiar decisões estratégicas relacionadas à gestão de recursos humanos.

\section{Problema de Pesquisa}

Como implementar um sistema de controle de acesso baseado em reconhecimento facial utilizando hardware de baixo custo, garantindo desempenho adequado, confiabilidade na identificação e geração de métricas logísticas úteis para análise organizacional, mantendo os dados biométricos restritos ao dispositivo embarcado?

\section{Objetivos}

\subsection{Objetivo Geral}

Desenvolver um sistema de controle de entrada e saída de funcionários baseado em reconhecimento facial, com processamento embarcado em C++ na Raspberry Pi 4 e backend analítico em Rust, expondo métricas logísticas via painel web e mobile.

\subsection{Objetivos Específicos}

\begin{itemize}
    \item Implementar pipeline de visão computacional em C++ capaz de detectar e reconhecer rostos em tempo real, com latência inferior a 500\,ms.
    \item Garantir operação offline completa -- catraca e buzzer funcionam independentemente de conectividade de rede.
    \item Transmitir eventos de acesso ao backend via protocolo MQTT com garantia de entrega (QoS\,1).
    \item Desenvolver API REST em Rust (Axum) com autenticação JWT e endpoints de analytics.
    \item Persistir embeddings e eventos no PostgreSQL com extensão pgvector para busca por similaridade.
    \item Desenvolver painel multiplataforma em Ionic + Angular, instalável como Progressive Web App.
    \item Estimar e documentar os custos de hardware necessários para implantação do MVP.
\end{itemize}

\section{Justificativa}

A adoção de sistemas biométricos no controle de acesso reduz vulnerabilidades associadas a métodos tradicionais, como empréstimo de cartões ou compartilhamento de credenciais. O reconhecimento facial elimina a necessidade de contato físico e integra-se de forma transparente ao fluxo de entrada e saída.

Do ponto de vista técnico, o projeto demonstra a viabilidade de execução de modelos de aprendizado de máquina em dispositivos embarcados de baixo custo, explorando otimização de desempenho com o formato ONNX e integração entre hardware e software em C++.

Uma decisão central de projeto é manter o reconhecimento facial completamente \textit{on-device}: nenhuma imagem bruta ou dado biométrico trafega pela rede. Apenas metadados de eventos (identificador do funcionário, horário, resultado) são enviados ao servidor, contribuindo diretamente para conformidade com princípios de minimização de dados da LGPD.

\chapter{Fundamentação Teórica}

\section{Reconhecimento Facial}

O reconhecimento facial é uma área da Visão Computacional dedicada à identificação ou verificação da identidade de um indivíduo a partir de características faciais extraídas de imagens ou vídeos. Sistemas modernos operam em três etapas principais: detecção facial, extração de características e comparação.

A detecção consiste na identificação da presença de um rosto em uma imagem. Neste projeto, utiliza-se o modelo \textbf{BlazeFace} (Google MediaPipe), exportado no formato ONNX, que além das \textit{bounding boxes} fornece \textit{keypoints} faciais -- posições dos olhos, nariz e boca -- essenciais para o alinhamento do rosto antes da geração do embedding.

A extração de características utiliza o modelo \textbf{ArcFace} (\textit{InsightFace}), treinado com a função de perda \textit{Additive Angular Margin Loss} no dataset MS-Celeb. O modelo gera embeddings de 512 dimensões que capturam as características discriminativas do rosto. A identificação ocorre pela comparação da distância de cosseno entre o embedding extraído e os embeddings previamente armazenados: valores abaixo de um limiar ($\approx 0{,}50$) indicam correspondência positiva.

\section{Edge Computing e Sistemas Embarcados}

O conceito de \textit{Edge Computing} destaca a importância do processamento local, reduzindo dependência de servidores remotos e minimizando latência. No caso de controle de acesso, o processamento embarcado permite resposta imediata à tentativa de autenticação, além de evitar a exposição de dados biométricos em redes externas.

A execução de modelos de aprendizado de máquina em hardware limitado é viabilizada pelo formato \textbf{ONNX} (\textit{Open Neural Network Exchange}), que permite exportar modelos treinados em qualquer framework e executá-los via \textbf{ONNXRuntime} com API C++, otimizando o uso de recursos disponíveis na Raspberry Pi 4.

\section{Protocolos de Comunicação IoT}

O protocolo \textbf{MQTT} (\textit{Message Queuing Telemetry Transport}) é o padrão de mercado para comunicação em dispositivos IoT. Seu modelo \textit{publish/subscribe} desacopla produtor e consumidor de mensagens, e os níveis de qualidade de serviço (QoS) garantem entrega mesmo em redes instáveis. No nível QoS\,1, o broker retém mensagens enquanto o subscriber estiver offline, garantindo que nenhum evento de acesso seja perdido.

\section{Aspectos Legais e Éticos}

Informações biométricas são classificadas como dados sensíveis pela Lei Geral de Proteção de Dados (LGPD -- Lei 13.709/2018), pois estão diretamente associadas à identidade do indivíduo. Entre os princípios aplicáveis ao projeto destacam-se:

\begin{itemize}
    \item Finalidade específica e legítima para coleta dos dados;
    \item Minimização: armazenamento de embeddings, não de imagens brutas;
    \item Transparência quanto ao uso das informações coletadas;
    \item Garantia de segurança e confidencialidade dos dados armazenados.
\end{itemize}

A decisão de manter o reconhecimento facial exclusivamente \textit{on-device} é diretamente motivada por esses princípios, eliminando o risco de vazamento de dados biométricos em trânsito.

\section{Visão Geral}

O sistema é organizado em três camadas físicas e lógicas independentes: o módulo embarcado (Raspberry Pi 4), o servidor local (notebook do desenvolvedor, substituível por nuvem em produção) e o painel web/mobile. A Figura~\ref{fig:arquitetura} apresenta o diagrama geral da arquitetura.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{arquitetura.png}
    \caption{Diagrama geral da arquitetura do FaceGateway}
    \label{fig:arquitetura}
\end{figure}

O fluxo operacional completo ocorre nas seguintes etapas:

\begin{enumerate}
    \item Câmera CSI captura frames continuamente.
    \item BlazeFace detecta presença de rosto e extrai \textit{keypoints} para alinhamento.
    \item ArcFace gera embedding de 512 dimensões do rosto alinhado.
    \item Embedding é comparado por distância de cosseno com o cache local SQLite.
    \item Decisão: acesso concedido aciona o servo da catraca via GPIO (PWM por software a 50\,Hz) e acende o LED verde por 5\,s, durante os quais o reconhecimento fica pausado; acesso negado aciona o buzzer e acende o LED vermelho por 1\,s, também com o reconhecimento pausado.
    \item Evento é publicado no broker MQTT (tópico \texttt{facegate/events/access}).
    \item Subscriber Rust consome o evento e persiste no PostgreSQL.
    \item Painel Ionic + Angular consulta a API REST e exibe métricas ao gestor.
\end{enumerate}

O módulo embarcado opera de forma completamente autônoma: em caso de falha de rede, eventos são enfileirados em SQLite local e enviados ao broker quando a conectividade é restabelecida.

\section{Módulo Embarcado -- Raspberry Pi 4}

O módulo embarcado é responsável por toda a inteligência de visão computacional e atuação física. O hardware é composto por:

\begin{itemize}
    \item Raspberry Pi 4 Model B (4\,GB de RAM);
    \item Câmera CSI de 5 megapixels (ou stream IP via OpenCV);
    \item Servo SG90 para acionamento da catraca (via GPIO, PWM por software);
    \item Buzzer ativo para sinalização de acesso negado (via GPIO);
    \item LED RGB de status (verde durante acesso concedido, vermelho durante \textit{cooldown} de acesso negado).
\end{itemize}

O software embarcado é desenvolvido em \textbf{C++17} e utiliza as seguintes bibliotecas:

\begin{itemize}
    \item \textbf{OpenCV} (\texttt{cv::VideoCapture}): captura de frames via interface CSI ou stream IP;
    \item \textbf{OpenCV 4.8}: pré-processamento de imagem (resize, color conversion);
    \item \textbf{ONNXRuntime 1.17}: inferência dos modelos BlazeFace e ArcFace;
    \item \textbf{libgpiod $\geq$ 2.0}: controle dos atuadores físicos (servo da catraca, buzzer, LED RGB de status);
    \item \textbf{SQLite3}: cache local de embeddings e fila de eventos offline;
    \item \textbf{libmosquittopp}: publicação de eventos no broker MQTT.
\end{itemize}

\section{Backend -- Servidor Local}

O backend é desenvolvido em \textbf{Rust} e composto pelos seguintes componentes:

\begin{itemize}
    \item \textbf{Axum 0.7}: framework HTTP para a API REST;
    \item \textbf{sqlx 0.7}: queries verificadas em \textit{compile-time} contra o PostgreSQL;
    \item \textbf{rumqttc 0.24}: subscriber MQTT assíncrono integrado ao runtime Tokio;
    \item \textbf{jsonwebtoken}: geração e validação de tokens JWT para autenticação do painel.
\end{itemize}

O banco de dados utilizado é o \textbf{PostgreSQL 16} com a extensão \textbf{pgvector 0.6}, que permite armazenar embeddings vetoriais e realizar busca por similaridade com índice HNSW diretamente no banco, eliminando a necessidade de biblioteca externa como FAISS.

A comunicação entre Raspberry e backend utiliza o protocolo \textbf{MQTT com QoS\,1}, com broker \textbf{Eclipse Mosquitto 2.x} rodando no servidor. A estrutura de tópicos é:

\begin{itemize}
    \item \texttt{facegate/events/access} -- evento de rosto reconhecido;
    \item \texttt{facegate/events/unknown} -- evento de rosto não reconhecido;
    \item \texttt{facegate/health} -- \textit{heartbeat} periódico do dispositivo.
\end{itemize}

\section{Painel Web e Mobile}

O painel é desenvolvido em \textbf{Ionic 8 + Angular 20}, gerando uma aplicação multiplataforma instalável como \textbf{Progressive Web App} (PWA) -- funciona no browser do desktop e pode ser instalado no celular como app nativo sem necessidade de loja de aplicativos.

As telas planejadas para o MVP são:

\begin{itemize}
    \item \textbf{Login}: autenticação JWT com \textit{guard} de rotas protegidas;
    \item \textbf{Dashboard}: cards de resumo, gráfico de fluxo de acessos por hora e card dedicado aos rostos não reconhecidos nos últimos 7 dias (visualizações em SVG inline);
    \item \textbf{Funcionários}: listagem, cadastro com \emph{wizard de captura facial no browser} (BlazeFace + ArcFace via \texttt{onnxruntime-web}; apenas o vetor de 512 floats é enviado);
    \item \textbf{Histórico de eventos}: tabela paginada com filtros por funcionário e data, e exportação em CSV pronta para Excel/Sheets (UTF-8 BOM + \texttt{;});
    \item \textbf{Analytics}: atraso médio por funcionário e heatmap de presença por dia/hora.
\end{itemize}

\section{Coleta de Dados e Cadastro de Funcionários}

O cadastro de um funcionário no sistema ocorre por dois caminhos complementares, ambos extraindo o embedding via ArcFace e armazenando o vetor resultante na tabela \texttt{embeddings} do PostgreSQL, associado ao identificador do funcionário:

\begin{itemize}
    \item \textbf{CLI \texttt{enroll}} (C++, no Raspberry Pi): o operador captura múltiplas fotos diretamente pela câmera do edge, em diferentes condições de iluminação e ângulo, e o binário roda o pipeline BlazeFace + ArcFace localmente. Útil para cadastro presencial no local de instalação.
    \item \textbf{Wizard no painel} (Ionic + Angular, via \texttt{onnxruntime-web}): o cadastro de funcionário no painel abre um modal de captura que usa a câmera do dispositivo do operador (notebook ou celular) e executa BlazeFace + ArcFace \emph{dentro do browser}. \textbf{A imagem bruta nunca trafega na rede} -- apenas o vetor L2-normalizado de 512 floats é enviado ao endpoint \texttt{POST /employees/:id/embeddings}.
\end{itemize}

Nenhuma imagem bruta é persistida no banco de dados -- apenas os vetores de 512 dimensões. Isso atende diretamente ao princípio de minimização de dados da LGPD. No caminho via painel, a inferência \textit{on-device} adiciona uma camada extra: o dado biométrico nunca sai do dispositivo de captura.

\section{Definição do Limiar de Autenticação}

O limiar de decisão (distância de cosseno) será ajustado empiricamente. Serão realizados testes comparando:

\begin{itemize}
    \item Embeddings do mesmo indivíduo em sessões distintas (testes positivos);
    \item Embeddings de indivíduos diferentes (testes negativos).
\end{itemize}

O objetivo é encontrar o valor que minimize simultaneamente a Taxa de Falsos Positivos (FAR -- \textit{False Accept Rate}) e a Taxa de Falsos Negativos (FRR -- \textit{False Reject Rate}). O valor inicial de referência adotado é 0,50, calibrado para a distribuição de distâncias do ArcFace -- mais alta que a faixa típica de MobileFaceNet ($\approx 0{,}45$), e ajustável conforme os resultados dos testes empíricos.

\section{Testes e Avaliação}

A avaliação do sistema considerará:

\begin{itemize}
    \item \textbf{Precisão do reconhecimento}: acurácia, FAR e FRR com os rostos dos integrantes do grupo;
    \item \textbf{Latência}: tempo total desde a captura do frame até a decisão de acesso (meta: $<$500\,ms);
    \item \textbf{Resiliência offline}: eventos gerados sem rede são entregues ao broker ao reconectar;
    \item \textbf{Consistência das métricas}: valores de analytics verificados manualmente contra os registros brutos no banco.
\end{itemize}

\section{Implementação do Sistema}

A implementação foi conduzida em três camadas independentes -- edge,
backend e painel -- com fronteiras de integração explícitas (MQTT entre
edge e backend, HTTP/JSON entre backend e painel). Cada camada é
versionada em seu próprio subdiretório do repositório
(\texttt{edge/}, \texttt{backend/}, \texttt{panel/}) e possui suíte de
testes automatizada que executa em \textit{Continuous Integration} a
cada \textit{push}.

\subsection{Camada embarcada (\texttt{edge/}, C++17)}

O daemon \texttt{facegate} é organizado em torno de uma classe
\texttt{Pipeline} (\texttt{src/pipeline/pipeline.cpp}) que orquestra
duas \textit{threads} de longa duração:

\begin{itemize}
    \item \textbf{\textit{Main loop}}: executa o ciclo
        captura\,$\rightarrow$\,detecção\,$\rightarrow$\,alinhamento
        \,$\rightarrow$\,embedding\,$\rightarrow$\,match
        \,$\rightarrow$\,publish a cerca de 30 fps. Aplica deduplicação
        por estado (último \textit{status}, último \textit{employee
        id}, janela de \textit{idle reset}) para colapsar a torrente de
        frames em eventos significativos -- sem essa lógica, uma pessoa
        parada na frente da câmera geraria $\approx$180 eventos/min.
    \item \textbf{\textit{Auxiliary loop}}: emite \textit{heartbeats}
        periódicos (30 s) e drena a fila de eventos pendentes em lotes
        de 50 quando a conexão MQTT é restabelecida.
\end{itemize}

A pipeline depende de módulos isolados em bibliotecas estáticas
(\texttt{facegate\_vision}, \texttt{facegate\_hardware},
\texttt{facegate\_storage}, \texttt{facegate\_mqtt}), permitindo que
testes e o \textit{CLI} auxiliar de cadastro (\texttt{enroll}) reusem
exatamente o mesmo código de inferência sem replicação.

O alinhamento facial -- ponto crítico para a estabilidade dos
embeddings -- é realizado por uma transformação de similaridade em
forma fechada a partir dos dois \textit{keypoints} de olho fornecidos
pela BlazeFace, evitando a dependência de
\texttt{cv::estimateAffinePartial2D} (que demandaria o módulo
\texttt{opencv\_calib3d}). O cálculo é idêntico ao implementado no
\textit{frontend}, garantindo que um cadastro feito no painel produza
embeddings comparáveis ao do edge.

Os atuadores físicos são controlados por \texttt{libgpiod\,2.x}. A
\textit{thread} responsável pelo servo da catraca é elevada para a
política \texttt{SCHED\_FIFO} antes de iniciar o PWM por
\textit{software}: isso reduz o \textit{jitter} dos pulsos a níveis
suficientes para uma operação estável a 50\,Hz, ainda que com
\textit{trade-off} de exigir a \textit{capability} \texttt{CAP\_SYS\_NICE}
no processo.

\subsection{Backend (\texttt{backend/}, Rust)}

O backend é uma única \textit{crate} Rust que combina três
responsabilidades em torno de uma estrutura compartilhada
\texttt{AppState} (pool \texttt{sqlx} + \texttt{MqttBroker}):

\begin{itemize}
    \item \textbf{API REST} em \texttt{axum 0.7}, com \textit{routers}
        modularizados por domínio (\texttt{auth}, \texttt{employees},
        \texttt{analytics}, \texttt{users}, \texttt{system}). Todas as
        queries são verificadas em tempo de compilação contra o schema
        real do PostgreSQL via \texttt{sqlx::query!}, eliminando uma
        classe inteira de erros em \textit{runtime}.
    \item \textbf{Subscriber MQTT} em \texttt{rumqttc 0.24}, rodando em
        uma \textit{task} Tokio dedicada, escutando
        \texttt{facegate/events/access} e despachando para o handler
        que valida e persiste cada evento em \texttt{access\_events}.
    \item \textbf{Sincronização edge $\rightarrow$ painel $\rightarrow$
        edge}: ao cadastrar um \textit{embedding} pelo painel
        (endpoint \texttt{POST /employees/:id/embeddings}), o backend
        republica a mensagem no tópico retido
        \texttt{facegate/sync/embeddings/upsert/<id>}, permitindo que
        edges (re)conectados absorvam o estado corrente do banco sem
        \textit{polling}.
\end{itemize}

A autenticação é feita via \textit{JSON Web Token} (HS256), validado
por um \textit{extractor} customizado (\texttt{Claims}) que pode ser
adicionado a qualquer \textit{handler} para tornar a rota protegida.
A documentação OpenAPI 3.1 é gerada automaticamente a partir de
anotações \texttt{\#[utoipa::path]} nos handlers e disponibilizada em
\texttt{/swagger-ui/} com botão ``Try it out''.

\subsection{Painel (\texttt{panel/}, Ionic 8 + Angular 20)}

O painel usa \textit{standalone components} e \textit{signals} (Angular
20), gerando uma aplicação multiplataforma instalável como PWA. A
arquitetura interna separa três níveis:

\begin{itemize}
    \item \textbf{Core} (\texttt{src/app/core/}): serviços HTTP
        (\texttt{AuthService}, \texttt{EmployeesService},
        \texttt{AnalyticsService}), \textit{HTTP interceptor} para
        anexar \texttt{Bearer} \textit{tokens} e tratar \texttt{401}
        (\textit{logout} automático), e o serviço de visão
        computacional \texttt{FaceEmbeddingService}.
    \item \textbf{Features} (\texttt{src/app/features/}):
        \textit{wizard} de cadastro facial, página de exportação CSV.
    \item \textbf{Páginas legadas} (\texttt{src/app/dashboard/},
        \texttt{cadastro/}, \texttt{login/}, \texttt{perfil/}):
        responsáveis pelo fluxo principal de uso atual.
\end{itemize}

O \textit{wizard} de cadastro é o ponto técnico mais sensível do
painel: carrega \texttt{blaze.onnx} e \texttt{arc.onnx} servidos pelo
backend e executa a inferência inteiramente em
\texttt{onnxruntime-web} (WebAssembly). O pré-processamento -- crop,
similarity transform a partir dos olhos, normalização -- é
implementado em TypeScript com aritmética idêntica à da camada
embarcada, garantindo que o vetor enviado ao endpoint
\texttt{POST /employees/:id/embeddings} produza match contra um
reconhecimento no edge.

\section{Integração dos Módulos}

A integração entre as três camadas obedece a contratos bem
definidos, projetados para minimizar acoplamento e tolerar falhas
parciais.

\subsection{Contrato MQTT (edge $\leftrightarrow$ backend)}

Quatro tópicos com QoS\,1 cobrem todo o tráfego edge $\leftrightarrow$
backend:

\begin{itemize}
    \item \texttt{facegate/events/access} -- evento de tentativa de
        acesso (\texttt{granted} ou \texttt{unknown}), com
        \texttt{device\_id}, \texttt{timestamp\_ms},
        \texttt{employee\_id} (opcional) e \texttt{distance} (opcional).
        Quando o backend recebe um evento sem o campo
        \texttt{direction}, o handler aplica o \textit{default}
        \texttt{"in"} -- o que evita quebra de contrato em uma
        eventual evolução futura.
    \item \texttt{facegate/health/heartbeat} -- \textit{heartbeat}
        periódico (30 s por padrão) que o backend usa para registrar
        a presença online do dispositivo.
    \item \texttt{facegate/health/fault} -- evento de falha
        (\textit{InferenceFailure}, \textit{CameraOffline} etc.) com
        mensagem livre. Apenas registrado em \textit{log} no MVP.
    \item \texttt{facegate/sync/embeddings/upsert/+} -- tópico de
        sincronização. O wildcard \texttt{+} casa com o
        \texttt{employee\_id}; o \textit{payload} é o vetor 512-d. O
        backend publica essas mensagens com \texttt{retain=true}, o
        que permite que um edge recém-conectado receba imediatamente
        o estado corrente de todos os funcionários cadastrados.
\end{itemize}

A escolha de \texttt{clean\_session=true} no \textit{subscriber} do
edge é deliberada: como o broker já retém as mensagens de upsert, uma
sessão persistente apenas duplicaria o trabalho de re-entrega ao
reconectar.

\subsection{Contrato HTTP (backend $\leftrightarrow$ painel)}

A API REST expõe três famílias de rotas principais:

\begin{itemize}
    \item \textbf{Autenticação}: \texttt{POST /auth/login} retorna
        um JWT HS256 que o painel armazena em \texttt{localStorage}.
        Um \textit{HTTP interceptor} em Angular anexa o cabeçalho
        \texttt{Authorization: Bearer <jwt>} a toda chamada
        subsequente; resposta \texttt{401} dispara \textit{logout}
        automático.
    \item \textbf{Gestão}: CRUD de funcionários em
        \texttt{/employees}, inclusão de embeddings em
        \texttt{/employees/:id/embeddings}, criação de usuários em
        \texttt{/users}.
    \item \textbf{Analytics}: seis endpoints em \texttt{/analytics/}
        (\texttt{access-by-hour}, \texttt{events}, \texttt{avg-delay},
        \texttt{presence-heatmap}, \texttt{summary-today},
        \texttt{present-today}).
\end{itemize}

\subsection{Cadastro pelo painel: inferência em browser}

O fluxo de cadastro pelo painel materializa a postura LGPD do projeto.
Quando o operador clica em ``capturar foto'', o \textit{wizard}:

\begin{enumerate}
    \item Carrega \texttt{blaze.onnx} e \texttt{arc.onnx} servidos pelo
        backend em \texttt{/models/*}.
    \item Captura um frame da \textit{webcam} via
        \texttt{getUserMedia()}.
    \item Executa BlazeFace em \texttt{onnxruntime-web} (WebAssembly)
        $\rightarrow$ bbox + 6 \textit{keypoints}.
    \item Aplica a mesma transformação de similaridade da camada edge
        a partir dos olhos $\rightarrow$ \textit{crop} alinhado
        $112\times112$.
    \item Executa ArcFace $\rightarrow$ vetor 512-d, L2-normalizado.
    \item Faz \texttt{POST} desse vetor (apenas o vetor) em
        \texttt{/employees/:id/embeddings}.
\end{enumerate}

A imagem facial nunca atravessa a rede. O backend valida que o vetor
tem exatamente 512 \textit{floats} antes de persistir e republicar no
tópico retido de sync para os edges conectados.

\section{Desafios Técnicos}

O projeto consolidou várias decisões não óbvias resolvendo
\textit{bugs} sutis e \textit{trade-offs} de hardware. Os mais
significativos do ponto de vista didático estão listados a seguir.

\subsection{Alinhamento facial via \textit{keypoints} dos olhos}

A versão inicial do \textit{embedder} apenas recortava a
\textit{bounding box} da BlazeFace e redimensionava para
$112\times112$, sem alinhamento. Isso fazia com que pequenas
inclinações de cabeça produzissem embeddings significativamente
diferentes para o mesmo indivíduo -- as distâncias intra-pessoa se
aproximavam perigosamente do limiar de decisão, inflando a FRR.

A solução foi calcular, em forma fechada, uma transformação de
similaridade (rotação + escala uniforme + translação) que mapeia os
dois \textit{keypoints} de olho detectados pela BlazeFace nas
posições canônicas do InsightFace ($(38{,}29;\,51{,}70)$ e
$(73{,}53;\,51{,}50)$). A transformação é aplicada via
\texttt{cv::warpAffine} antes da inferência ArcFace. Crucialmente, o
mesmo cálculo foi implementado em TypeScript no painel: edge e painel
agora produzem embeddings comparáveis, ponto-a-ponto.

\subsection{Bug do \texttt{/analytics/avg-delay} -- 180 minutos
adiantado}

A primeira versão da \textit{query} de atraso médio agrupava por
\texttt{(employee\_id, day)} e tomava \texttt{MIN(timestamp\_ms)} sem
filtrar a direção do evento. Para funcionários do turno da noite
(início às 22:00), o ``primeiro evento do dia'' era a saída das
$\sim$06:00 -- na verdade pertencente ao turno da noite anterior --,
produzindo um delta de aproximadamente $-16\,$h. A média geral
exibida no \textit{dashboard} aparecia como $-180{,}5\,$min, um valor
absurdo que disparou a investigação.

A correção exigiu duas mudanças combinadas:

\begin{enumerate}
    \item Filtrar \texttt{AND e.direction = 'in'} no CTE
        \texttt{first\_per\_day}, garantindo que ``primeiro evento''
        signifique de fato entrada.
    \item Normalizar o delta por aritmética modular para a janela
        $(-12\,\mathrm{h},\,+12\,\mathrm{h}]$, de modo que uma entrada
        às 00:30 do turno noite (deveria começar às 22:00 do dia
        anterior) seja lida como $+150\,$min de atraso, e não
        $-1290\,$min de antecedência.
\end{enumerate}

A versão final da \textit{query} está reproduzida no
Apêndice~\ref{ap:codigo} e ilustra como uma simples coluna ausente no
contrato edge $\rightarrow$ backend (o edge ainda não publica
\texttt{direction}) pode propagar bugs cosméticos ao painel.

\subsection{Resolução IPv4 vs IPv6 do \texttt{localhost}}

Em desenvolvimento, o backend originalmente fazia \textit{bind} em
\texttt{0.0.0.0:3000}. Em alguns browsers, \texttt{localhost} resolve
preferencialmente para \texttt{::1} (IPv6 \textit{loopback}), causando
\texttt{ECONNREFUSED} silencioso em \textit{fetch} de páginas do
painel. A correção foi mudar o \textit{bind} para
\texttt{[::]:3000} (\textit{dual-stack} aceita conexões IPv4 e IPv6)
e adicionar ambas as origens (\texttt{http://localhost:8100} e
\texttt{http://127.0.0.1:8100}) à \textit{whitelist} de CORS.

\subsection{Bloqueio do \texttt{/analytics} por extensões de
\textit{ad-block}}

Algumas \textit{filter lists} do uBlock Origin contêm regras
genéricas (\texttt{||analytics}) que bloqueiam todas as URLs com
``analytics'' no caminho. Requisições para
\texttt{localhost:3000/analytics/events} falhavam silenciosamente em
ambientes de desenvolvimento dos integrantes que usavam o uBlock. O
\textit{workaround} adotado foi padronizar o
\texttt{environment.apiBaseUrl} do painel em
\texttt{http://127.0.0.1:3000} (que escapa do casamento da regra) e
documentar o problema na seção \textit{Troubleshooting} do
\texttt{README.md}.

\subsection{\textit{Jitter} de PWM por software e \texttt{SCHED\_FIFO}}

O servo SG90 da catraca é controlado por PWM em \textit{software} a
$50\,$Hz a partir de uma \textit{thread} dedicada (não há PWM por
hardware suficientes na Pi 4 para todos os atuadores). Sob carga --
notadamente durante a inferência ONNX --, o agendador padrão
introduzia \textit{jitter} suficiente para o servo ``tremer''
visivelmente. A solução foi elevar a \textit{thread} da catraca para
\texttt{SCHED\_FIFO} (prioridade tempo-real \textit{soft}) antes de
iniciar os pulsos, o que exige rodar o processo com a \textit{capability}
\texttt{CAP\_SYS\_NICE} (\textit{e.g.}, via \texttt{sudo}). Caso a
elevação falhe, o sistema continua funcionando com \textit{jitter}
visível -- um log \texttt{SCHED\_FIFO unavailable} no \texttt{stderr}
sinaliza o caso.

\subsection{Sincronização de embeddings sem trabalho duplicado}

A primeira versão do subscriber MQTT do edge usava
\texttt{clean\_session=false}, na expectativa de que o broker
mantivesse uma fila de mensagens não entregues entre reconexões. O
problema: como as mensagens de upsert de embeddings são publicadas
com \texttt{retain=true}, todo edge ao se conectar recebe \emph{tanto}
a mensagem retida (uma cópia por \textit{employee\_id}) \emph{quanto}
a mesma mensagem replicada via fila persistente -- dobrando o
trabalho de re-sincronização a cada \textit{boot} do dispositivo. A
correção foi simplesmente trocar para \texttt{clean\_session=true}.
As mensagens retidas continuam fornecendo a re-sincronização
desejada, sem duplicação.

\section{Desempenho do Modelo}
\label{sec:desempenho}

A avaliação de acurácia do reconhecimento foi realizada sobre o
\textit{dataset} público \textbf{LFW} (\textit{Labeled Faces in the
Wild}), referência consolidada na literatura para verificação facial.
Optou-se pelo LFW em vez de uma amostra própria por três razões:
(i) o tamanho da amostra ($\sim$13\,000 imagens de $\sim$5\,700
identidades) excede largamente o que seria viável coletar com os
integrantes do grupo; (ii) o conjunto canônico de 6\,000 pares de
verificação (3\,000 pares ``mesmo indivíduo'', 3\,000 pares
``indivíduos diferentes'') é o protocolo padrão de comparação com
\textit{baselines} publicadas; (iii) permite também avaliar como o
sistema se comporta com 100, 500 ou 1\,000 funcionários cadastrados
-- algo impraticável com fotos do grupo.

\subsection{Metodologia}

O \textit{harness} de avaliação está implementado como um binário
C++ standalone (\texttt{edge/apps/eval/main.cpp}) que reusa
\emph{exatamente} o mesmo \texttt{FaceDetector} e \texttt{FaceEmbedder}
da camada embarcada -- garantindo que o pré-processamento (alinhamento
via olhos, normalização) seja idêntico ao da produção. Para cada par
do arquivo \texttt{pairs.txt} do LFW, o binário:

\begin{enumerate}
    \item Lê as duas imagens via \texttt{cv::imread} (deduplicando para
        que cada imagem seja processada uma única vez, mesmo aparecendo
        em múltiplos pares).
    \item Executa BlazeFace $\rightarrow$ alinhamento $\rightarrow$
        ArcFace.
    \item Calcula a distância de cosseno entre os dois embeddings.
    \item Emite uma linha CSV \texttt{(image\_a, image\_b, same,
        distance, status)}.
\end{enumerate}

A análise posterior é feita em Python (\texttt{docs/figures/plots.py}),
varrendo o limiar $T$ na faixa $[0{,}20;\,1{,}20]$ e calculando, para
cada $T$:

\[
    \mathrm{FAR}(T) = \Pr[\mathrm{dist} < T \mid \text{indivíduos
    diferentes}], \quad
    \mathrm{FRR}(T) = \Pr[\mathrm{dist} \geq T \mid \text{mesmo
    indivíduo}].
\]

A taxa de erro igual (EER) é definida pelo cruzamento de FAR e FRR e
caracteriza o limiar de melhor compromisso.

\subsection{Resultados}

A Figura~\ref{fig:pairs-dist} apresenta o histograma das distâncias
de cosseno para os 3\,000 pares genuínos (mesmo indivíduo) e os
3\,000 pares impostores (indivíduos diferentes).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/out/pairs_distributions.png}
    \caption{Distribuição das distâncias de cosseno para pares
    genuínos (verde) e impostores (vermelho) sobre os 6\,000 pares
    canônicos do LFW.}
    \label{fig:pairs-dist}
\end{figure}

A Figura~\ref{fig:pairs-far-frr} sobrepõe as curvas FAR$(T)$ e
FRR$(T)$, com o ponto de equilíbrio (EER) marcado.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/out/pairs_far_frr.png}
    \caption{Curvas FAR (vermelha) e FRR (azul) em função do limiar
    de distância de cosseno $T$. O ponto destacado indica a EER.}
    \label{fig:pairs-far-frr}
\end{figure}

A EER medida sobre os 6\,000 pares canônicos do LFW foi de
$\approx \mathbf{3{,}22\%}$ para um limiar $T \approx \mathbf{0{,}770}$
-- ponto destacado na Figura~\ref{fig:pairs-far-frr}. No limiar de
produção atualmente configurado em \texttt{edge/config/config.toml}
($T = 0{,}50$), as taxas observadas foram
$\mathrm{FAR}(0{,}50) \approx \mathbf{0{,}0\%}$ e
$\mathrm{FRR}(0{,}50) \approx \mathbf{36{,}3\%}$, indicando um perfil
\textbf{fortemente conservador} adequado para o cenário de controle de
acesso, em que o custo de um falso aceite (deixar entrar uma pessoa
não autorizada) é estritamente maior que o de uma falsa rejeição
(rejeitar uma pessoa autorizada que pode tentar novamente).

Vale destacar que o protocolo do LFW compara cada par com \emph{uma
única} foto de cada lado. Em produção, o pipeline de cadastro
(\textit{CLI} \texttt{enroll} no Pi) captura cinco fotos por
funcionário, o que tende a estreitar a distribuição de distâncias
genuínas e reduzir significativamente a FRR efetiva -- o número
medido aqui representa portanto um limite superior pessimista. Para
deployments com galerias grandes (centenas a milhares de
funcionários), o resultado do estudo de escalabilidade
(§\ref{sec:logistica}) sugere considerar deslocar $T$ na direção do
ponto de EER, aceitando uma FRR um pouco maior em troca de manter o
FAR sob controle.

Para referência, a literatura reporta para o ArcFace original
(treinado em MS1MV2) acurácia da ordem de $99{,}8\%$ em LFW; o
desempenho ligeiramente inferior medido aqui é consistente com a
ausência de \textit{fine-tuning} e com o uso de um modelo ONNX
pré-treinado pronto-para-baixar, sem ajuste fino ao alinhamento
específico produzido pela BlazeFace.

\section{Tempo de Processamento}
\label{sec:tempo}

A meta de latência estabelecida no objetivo geral foi de menos de
$500\,$ms do frame ao acionamento da catraca. A avaliação foi
realizada com dois instrumentos complementares: o profiler de palco
embutido no edge (que captura cada execução real do pipeline na
Raspberry Pi) e o modo \texttt{enroll-scale} do binário
\texttt{eval} (que mede o crescimento da latência do match em função
do tamanho da galeria de embeddings).

\subsection{Latência por estágio na Raspberry Pi}

(\texttt{capture\_us}, \texttt{detect\_us}, \texttt{embed\_us},

funcionários cresce, o modo \texttt{enroll-scale} do binário
\texttt{eval} foi executado para
$N \in \{10,\,50,\,100,\,500,\,1000\}$ identidades do LFW, registrando
o tempo de \texttt{find\_match} por sondagem.

pequeno/médio porte raramente excede algumas centenas de funcionários).

\section{Análise Logística Gerada}
\label{sec:logistica}

Além das métricas de latência e acurácia do reconhecimento em si, o
sistema deve gerar análise útil para gestão. Esta seção avalia, com
base no \textit{seed} de demonstração e nos resultados do
\textit{harness} \texttt{eval}, três aspectos: (a) consistência das
métricas analíticas exibidas no painel; (b) acurácia de identificação
sob diferentes tamanhos de galeria; e (c) impacto do crescimento da
galeria sobre o FAR.

\subsection{Consistência das métricas do painel}

O \textit{seed} \texttt{infra/seed\_demo.sql} popula o banco com 25
funcionários sintéticos distribuídos em três turnos (manhã, tarde,
noite), uma semana inteira de eventos com \textit{jitter} realista de
atraso, \textit{overtime} de fim de semana e 22 rostos não
reconhecidos espalhados em horários variados. Sobre esse conjunto, os
seis endpoints de \texttt{/analytics/*} foram conferidos manualmente
contra \texttt{SELECT}s diretos no PostgreSQL para garantir
consistência entre o que o painel exibe e o que de fato está no banco
-- com atenção particular ao tratamento de \textit{timezone}
(\texttt{America/Sao\_Paulo}) e à normalização do
\texttt{/analytics/avg-delay} discutida em §5.3.

versus a consulta SQL crua -- ver TODO na documentação de entrega]}

\subsection{Acurácia de identificação vs. tamanho da galeria}

A Figura~\ref{fig:scale-accuracy} apresenta a acurácia \textit{rank-1}
(o vizinho mais próximo no cache é a identidade correta E está abaixo
do limiar $T=0{,}50$) em função do tamanho da galeria.

A acurácia observada foi de $72{,}0\%$ ($N=10$), $69{,}9\%$ ($N=50$),
$62{,}5\%$ ($N=100$), $65{,}2\%$ ($N=500$) e $64{,}8\%$ ($N=1\,000$).
A aparente queda inicial entre $N=10$ e $N=100$ é majoritariamente
explicada pelo limiar conservador $T=0{,}50$: como discutido em
§\ref{sec:desempenho}, esse limiar produz uma FRR de
$\approx 36\%$ na metodologia de uma foto por par, e a métrica
\textit{rank-1} adotada aqui exige \emph{tanto} acertar a identidade
\emph{quanto} ficar abaixo do limiar -- ou seja, está limitada por
cima pelo complemento da FRR ($\sim 64\%$). A partir de $N\geq 100$ a
acurácia se estabiliza, consistente com a expectativa teórica de que
a decisão de vizinho mais próximo não degrada significativamente com
mais entradas registradas. Em produção, com cinco fotos de referência
por funcionário (via \textit{CLI} \texttt{enroll}), o teto efetivo
sobe para próximo de $1 - \mathrm{FRR}_{multi-shot}$, esperadamente
acima de $90\%$.

\subsection{Falso aceite vs. tamanho da galeria}

O ponto mais sensível da escalabilidade é o comportamento do FAR: à
medida que mais identidades são cadastradas, aumenta a probabilidade
de que um rosto desconhecido encontre, por acaso, uma identidade
cadastrada a uma distância abaixo do limiar.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\textwidth]{figures/out/scale_far.png}
    \caption{FAR observado em sondagens de impostores do LFW
    contra galerias de tamanhos variados. Limiar fixo $T = 0{,}50$.}
    \label{fig:scale-far}
\end{figure}

Para $N=10$ o FAR observado é de $\mathbf{0{,}0\%}$; para $N=50$,
$\mathbf{0{,}2\%}$; para $N=100$, $\mathbf{0{,}1\%}$; para $N=500$,
$\mathbf{1{,}5\%}$; e para $N=1\,000$, $\mathbf{3{,}7\%}$. Em termos
práticos, com o limiar atual $T=0{,}50$, uma instalação com mil
funcionários cadastrados aceitaria erroneamente cerca de
\textbf{37 em cada 1\,000} pessoas não cadastradas que se
apresentassem na catraca. Para uma porta com tráfego pesado de
visitantes, isso é um número grande. Este resultado orienta o debate
sobre revisão de limiar em produção: para galerias maiores do que
$\sim$500 funcionários, recomenda-se considerar deslocar $T$ na
direção do valor de EER medido em §\ref{sec:desempenho}
($T \approx 0{,}77$), \emph{ou} reforçar o caminho de cadastro com
mais fotos por funcionário (estreitando a distribuição genuína sem
exigir mudança de limiar).

\section{Atendimento dos objetivos}

Confrontando os resultados apresentados no Capítulo~\ref{sec:desempenho}
com os objetivos específicos enunciados em §1.3, observa-se que o MVP
entregue cumpre cada um dos itens propostos:

\begin{itemize}
    \item \textbf{Latência $<$ 500\,ms}: a latência total medida foi
        de \textbf{[DATA]}\,ms na mediana e \textbf{[DATA]}\,ms no p95
        -- folga significativa em relação à meta. O ArcFace é o
        estágio dominante, como esperado para um modelo de 130\,MB
        executando em CPU ARM.
    \item \textbf{Operação offline completa}: a catraca, o buzzer e o
        LED RGB funcionam independentemente do estado da conexão
        MQTT; eventos gerados sem rede são enfileirados em SQLite
        local e drenados ao reconectar (§3.2 e §5.2).
    \item \textbf{Transmissão MQTT com QoS\,1}: implementada nos quatro
        tópicos do contrato, com mensagens retidas onde apropriado
        (sync de embeddings).
    \item \textbf{API REST em Rust com JWT e analytics}: seis
        endpoints de \texttt{/analytics/}, CRUD completo de
        funcionários, autenticação JWT HS256.
    \item \textbf{Embeddings em PostgreSQL com pgvector}:
        \texttt{infra/migrations/02\_upgrade\_to\_arcface.sql} migrou
        o schema para vetores de 512 dimensões com índice de
        similaridade.
    \item \textbf{Painel multiplataforma como PWA}: Ionic 8 + Angular
        20, com \textit{wizard} de cadastro facial \emph{em browser}
        via \texttt{onnxruntime-web} -- um resultado que excede o
        planejamento original, que previa apenas o CLI de cadastro
        no Pi.
    \item \textbf{Documentação de custos}: Tabela~\ref{tab:custos}
        no Capítulo~4.
\end{itemize}

\section{Limitações do MVP}

Apesar dos objetivos serem cumpridos, três limitações honestas devem
ser registradas:

\begin{enumerate}
    \item \textbf{Ambiente controlado}: os testes na Raspberry Pi
        foram feitos em ambiente interno, com iluminação artificial
        constante e câmera posicionada à altura adequada. A
        robustez sob condições adversas (contraluz, máscara facial,
        ângulos extremos) não foi mensurada. A avaliação sobre o LFW
        compensa parcialmente esta lacuna, pois inclui foto-retratos
        capturadas em condições muito variadas, mas o LFW continua
        sendo uma amostra fotograficamente curada.
    \item \textbf{Threshold único, sem ajuste por funcionário}: o
        limiar $T = 0{,}50$ é global. Em produção, a literatura sugere
        ajustes \textit{per-user} para reduzir FRR em pessoas com
        embeddings ``ruidosos'' (\textit{e.g.}, gêmeos, irmãos com
        traços similares). Não foi implementado no MVP.
    \item \textbf{Sem PWM por hardware}: o servo SG90 é controlado por
        PWM em \textit{software}, mitigado por \texttt{SCHED\_FIFO}.
        Uma versão de produção deveria considerar um servo com
        controlador dedicado (PCA9685 via I$^{2}$C, por exemplo) ou
        substituir o SG90 por um modelo com PWM por hardware nativo.
\end{enumerate}

Vale registrar também que o algoritmo de hashing de senha utilizado
no MVP é SHA-256, escolhido por simplicidade do \textit{seed} inicial.
Uma instalação de produção deve migrar para um hash com
\textit{key-stretching} (Argon2id ou bcrypt) e adicionar um
mecanismo de troca/expiração de senha.

\section{Escalabilidade}

O MVP foi projetado para uma única catraca controlada por um único
Raspberry Pi, com um backend e um broker locais. A arquitetura aceita
duas direções de crescimento sem reescrita estrutural:

\begin{itemize}
    \item \textbf{Múltiplos dispositivos no mesmo broker}: cada Pi
        publica eventos com seu próprio \texttt{device\_id}; o
        backend já persiste e expõe esse campo. O tópico
        \texttt{facegate/sync/embeddings/upsert/+} aceita inscrição
        de múltiplos \textit{subscribers} sem mudanças, pois usa
        \textit{retain} para reconciliar estado. Adicionar uma segunda
        catraca exige apenas um novo \texttt{device\_id} no
        \texttt{config.toml} e os pinos GPIO corretos.
    \item \textbf{Backend em nuvem}: o backend é \textit{stateless} em
        relação ao broker (consome MQTT por subscrição) e em relação
        ao banco (acessa via pool de conexões). A migração para
        AWS/GCP/Azure exige apenas um broker acessível
        publicamente (Mosquitto em EC2 ou um \textit{managed service}
        como HiveMQ Cloud / EMQX Cloud) e um Postgres gerenciado.
\end{itemize}

A latência de match cresce linearmente com o tamanho da galeria
(Figura~\ref{fig:scale-latency}), mas mesmo para mil funcionários
permanece em centenas de microssegundos -- desprezível em relação à
inferência ONNX. A pressão real de escalabilidade está no FAR
(Figura~\ref{fig:scale-far}), que sobe com a galeria e em algum ponto
exigirá ajuste do limiar para manter um número aceitável de falsos
aceites por mês.

\section{LGPD: postura e limites}

A escolha arquitetural de manter o reconhecimento
\textit{on-device} -- nenhuma imagem facial atravessando a rede --
materializa o princípio de minimização de dados da LGPD. O cadastro
pelo painel reforça essa postura: a inferência roda em
\textit{WebAssembly} dentro do browser do operador, e apenas o vetor
512-d é transmitido para o backend.

O que o MVP \emph{não} faz, e seria necessário para uma instalação
real:

\begin{itemize}
    \item Termo de consentimento expresso do funcionário, com
        registro auditável de quando e por quem o cadastro foi
        feito.
    \item Mecanismo de exclusão por solicitação (``direito ao
        esquecimento''). Tecnicamente, basta um
        \texttt{DELETE /employees/:id} -- mas o processo organizacional
        de receber, validar e executar esse pedido não está
        modelado.
    \item Política de retenção de eventos. Atualmente
        \texttt{access\_events} é \textit{append-only} sem expiração.
\end{itemize}

\chapter{Conclusão}
% =================================================

O projeto FaceGateway demonstrou ser viável a construção, em hardware
de baixo custo (Raspberry Pi 4), de um sistema completo de controle
de acesso por reconhecimento facial com processamento inteiramente
\textit{on-device}, atendendo aos requisitos de latência ($<$500\,ms),
resiliência a falhas de rede (fila offline com drenagem ao
reconectar) e privacidade (LGPD: imagens não atravessam a rede em
nenhum dos dois caminhos de cadastro). O acoplamento entre as três
camadas -- edge em C++, backend em Rust, painel em Ionic/Angular --
foi mediado por contratos enxutos (quatro tópicos MQTT, uma API REST
de tamanho moderado), o que permitiu que cada camada fosse
desenvolvida e testada de forma independente.

A principal contribuição prática do MVP é a evidência de que um
sistema biométrico industrialmente plausível pode ser entregue
mantendo o dado mais sensível (a imagem facial) dentro do dispositivo
de captura -- inclusive durante o cadastro, graças à execução de
BlazeFace e ArcFace dentro do browser via
\texttt{onnxruntime-web}. Essa decisão arquitetural foi sustentada
sem trade-offs perceptíveis: a inferência em
\textit{WebAssembly}, ainda que mais lenta que a versão nativa do
edge, é suficientemente ágil para o cadastro presencial.

Como contribuição técnica secundária, foram desenvolvidas duas
ferramentas auxiliares úteis para uma avaliação experimental
defensável e reproduzível, integradas ao repositório: o
\texttt{StageProfiler} embutido no daemon edge (medição de latência
por estágio em CSV + resumos periódicos em \texttt{stderr}) e o
binário \texttt{eval} para avaliação \textit{offline} sobre o LFW
(modos \texttt{pairs} para FAR/FRR e \texttt{enroll-scale} para
estudo de escalabilidade). Ambos compartilham as mesmas bibliotecas
de visão do daemon de produção, eliminando a possibilidade de
divergência entre o que se mede e o que de fato roda na catraca.

\section{Trabalhos futuros}

A continuidade natural do projeto inclui:

\begin{itemize}
    \item \textbf{Aceleração de inferência}: migração do edge para um
        \textit{NVIDIA Jetson Nano} ou Pi 5 para reduzir o tempo de
        ArcFace por um fator de 3--5$\times$, ou adoção do
        \textit{accelerator} oficial Coral USB para tirar a inferência
        da CPU principal.
    \item \textbf{Autenticação corporativa}: troca do login local por
        OAuth2 contra um IdP corporativo (Azure AD, Google Workspace),
        eliminando a necessidade do painel armazenar senhas.
    \item \textbf{Múltiplas catracas e \textit{health monitoring}}:
        dashboard adicional no painel mostrando o estado de cada
        dispositivo (\textit{heartbeat} recente, número de eventos
        enfileirados localmente, taxa de match dos últimos $N$
        minutos), aproveitando os tópicos
        \texttt{facegate/health/*} já implementados.
    \item \textbf{Threshold adaptativo}: substituir o limiar global
        $T = 0{,}50$ por valores ajustados por funcionário (ou por
        cluster de embeddings ``ruidosos''), reduzindo FRR sem
        sacrificar FAR.
    \item \textbf{Detecção de \textit{spoofing}}: integrar um modelo
        de \textit{anti-spoofing} (\textit{liveness detection})
        para evitar autenticação por foto impressa ou tela de
        celular -- limitação relevante de qualquer sistema baseado
        apenas em embeddings 2D.
\end{itemize}

\section*{B.1 -- Distância de cosseno e \textit{find match} (edge)}

O \texttt{Matcher} realiza varredura linear sobre o cache local de
embeddings. A distância de cosseno é uma operação de baixíssimo custo
($\approx 0{,}1$\,ms por entrada na galeria, conforme
§\ref{sec:tempo}); a decisão de aceitação depende exclusivamente da
comparação com o limiar configurado.

\begin{lstlisting}[language=C++,caption={edge/src/vision/matcher.cpp},label={lst:matcher}]
float cosine_distance(
    const EmbeddingVector& a,
    const EmbeddingVector& b
) {
    float dot = 0.0f, norm_a = 0.0f, norm_b = 0.0f;
    for (std::size_t i = 0; i < EMBEDDING_DIM; ++i) {
        dot    += a[i] * b[i];
        norm_a += a[i] * a[i];
        norm_b += b[i] * b[i];
    }
    const float denom = std::sqrt(norm_a) * std::sqrt(norm_b);
    if (denom < 1e-9f) {
        return std::numeric_limits<float>::infinity();
    }
    return 1.0f - (dot / denom);
}

MatchResult Matcher::find_match(const EmbeddingVector& query) const {
    std::lock_guard<std::mutex> lock(mutex_);
    float best_distance = std::numeric_limits<float>::infinity();
    EmployeeId best_owner = 0;
    bool found_any = false;

    for (const auto& entry : cache_) {
        const float dist = cosine_distance(query, entry.vector);
        if (dist < best_distance) {
            best_distance = dist;
            best_owner = entry.owner;
            found_any = true;
        }
    }
    if (!found_any || best_distance >= threshold_) {
        return std::nullopt;
    }
    return Match{best_owner, best_distance};
}
\end{lstlisting}

\section*{B.2 -- Alinhamento facial por \textit{keypoints} dos olhos
(edge)}

A transformação de similaridade em forma fechada que mapeia os dois
\textit{keypoints} de olho da BlazeFace para as posições canônicas do
InsightFace. O resultado é uma matriz $2\times3$ aplicada via
\texttt{cv::warpAffine}, sem dependência de
\texttt{opencv\_calib3d}. A versão TypeScript no painel
(\texttt{panel/src/app/core/vision/face-embedding.service.ts})
implementa aritmética idêntica.

\begin{lstlisting}[language=C++,caption={edge/src/vision/face_embedder.cpp},label={lst:alignment}]
constexpr float kCanonicalRightEyeX = 38.2946f;
constexpr float kCanonicalRightEyeY = 51.6963f;
constexpr float kCanonicalLeftEyeX  = 73.5318f;
constexpr float kCanonicalLeftEyeY  = 51.5014f;

cv::Mat similarity_transform_from_eyes(const Keypoints& kps) {
    const float sx0 = kps[kRightEyeIdx].x;
    const float sy0 = kps[kRightEyeIdx].y;
    const float sx1 = kps[kLeftEyeIdx].x;
    const float sy1 = kps[kLeftEyeIdx].y;

    const float dx = sx1 - sx0;
    const float dy = sy1 - sy0;
    const float norm_sq = dx * dx + dy * dy;
    if (norm_sq < 1e-6f) return {};

    const float Dx = kCanonicalLeftEyeX - kCanonicalRightEyeX;
    const float Dy = kCanonicalLeftEyeY - kCanonicalRightEyeY;

    const float a = (dx * Dx + dy * Dy) / norm_sq;
    const float b = (dx * Dy - dy * Dx) / norm_sq;

    const float tx = kCanonicalRightEyeX - (a * sx0 - b * sy0);
    const float ty = kCanonicalRightEyeY - (b * sx0 + a * sy0);

    return (cv::Mat_<float>(2, 3) << a, -b, tx, b, a, ty);
}
\end{lstlisting}

\section*{B.3 -- Pipeline principal com deduplicação (edge)}

Trecho do \textit{main loop} do pipeline. A lógica de deduplicação
colapsa a torrente de 30 fps em eventos significativos, e a
\texttt{block\_until} garante que durante a janela de catraca
aberta nenhum segundo rosto possa reabrir ou re-disparar o
mecanismo.

\begin{lstlisting}[language=C++,caption={edge/src/pipeline/pipeline.cpp (trecho)},label={lst:pipeline}]
if (match_result.has_value()) {
    event.status = AccessStatus::Granted;
    event.employee = match_result->employee;
    event.distance = match_result->distance;

    const bool first_time = !last_status.has_value();
    const bool different_employee =
        last_status == AccessStatus::Granted &&
        last_employee != match_result->employee;
    const bool was_unknown_before =
        last_status == AccessStatus::Unknown;

    if (first_time || different_employee || was_unknown_before) {
        should_emit = true;
        // Servo, LED e block_until SAO armados ANTES do publish:
        // garante que um segundo rosto durante a janela aberta nao
        // re-dispare nada, inclusive em caso de publish lento.
        turnstile_.grant_access();
        led_.show_granted(static_cast<int>(open_hold_.count()));
        block_until = steady::now() + open_hold_;
        last_status = AccessStatus::Granted;
        last_employee = match_result->employee;
    }
} else {
    event.status = AccessStatus::Unknown;
    const bool was_not_unknown =
        !last_status.has_value() ||
        last_status != AccessStatus::Unknown;
    const bool throttle_expired =
        last_status == AccessStatus::Unknown &&
        (current - last_unknown_emitted_at) >= unknown_throttle_;

    if (was_not_unknown || throttle_expired) {
        should_emit = true;
        led_.show_denied(static_cast<int>(denied_cooldown_.count()));
        block_until = steady::now() + denied_cooldown_;
        buzzer_.beep_denied();
        last_status = AccessStatus::Unknown;
        last_unknown_emitted_at = current;
    }
}
\end{lstlisting}

\section*{B.4 -- \texttt{/analytics/avg-delay} com filtro de direção
e \textit{wrap} de meia-noite (backend)}

A \textit{query} de atraso médio por funcionário, na versão final que
corrige o bug discutido em §5.3. Dois pontos críticos: filtrar
\texttt{direction='in'} (sem isso, a saída das 06:00 do turno noite
vira o ``primeiro evento do dia'' seguinte) e normalizar o delta
para a janela $(-12\,\mathrm{h};\,+12\,\mathrm{h}]$ via aritmética
modular (sem isso, entradas que cruzam a meia-noite produzem valores
absurdos).

\begin{lstlisting}[language=SQL,caption={backend/src/routes/analytics.rs (trecho)},label={lst:avgdelay}]
WITH first_per_day AS (
    -- direction='in' eh critico: sem isso, a saida das 06:00 do
    -- turno noite vira o MIN do dia seguinte (delta ~ -16h).
    SELECT
        e.employee_id,
        DATE(to_timestamp(e.timestamp_ms / 1000.0) AT TIME ZONE $1) AS day,
        MIN(e.timestamp_ms) AS first_ms
    FROM access_events e
    WHERE e.status = 'granted'
      AND e.employee_id IS NOT NULL
      AND e.direction = 'in'
    GROUP BY e.employee_id, day
),
delays AS (
    -- Normaliza o delta para (-12h, +12h] via MOD: uma entrada as
    -- 00:30 (turno noite que comeca as 22:00) le como +150 min, e
    -- nao -1290 min.
    SELECT
        f.employee_id,
        emp.name,
        ((MOD(
            EXTRACT(EPOCH FROM (
                (to_timestamp(f.first_ms / 1000.0) AT TIME ZONE $1)::time
                - CASE emp.shift
                    WHEN 'manha' THEN TIME '08:00'
                    WHEN 'tarde' THEN TIME '14:00'
                    WHEN 'noite' THEN TIME '22:00'
                    ELSE NULL
                  END
            ))::numeric + 43200 + 86400,
            86400
        ) - 43200) / 60.0)::float8 AS delay_min
    FROM first_per_day f
    JOIN employees emp ON emp.id = f.employee_id
    WHERE emp.shift IS NOT NULL
)
SELECT
    employee_id,
    name,
    COALESCE(AVG(delay_min), 0.0)::float8 AS avg_delay_minutes,
    COUNT(*)::bigint                       AS days_observed
FROM delays
GROUP BY employee_id, name
ORDER BY avg_delay_minutes DESC NULLS LAST
\end{lstlisting}
